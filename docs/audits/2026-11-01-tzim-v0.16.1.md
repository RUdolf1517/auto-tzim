## Limits — what this audit did not do

**Nothing was executed.** No `tzim` binary was run: the release assets are served from `release-assets.githubusercontent.com`,
which this environment cannot reach, and there is no Rust toolchain to build one. Every statement below is a statement
about **source and published documentation at `f605c2ea`**, not about observed behaviour. When AT-08 runs the pinned
binary in CI, the same table must be re-checked against real output — that check is part of what the pin is for.

This matters more than usual, because the drift found here is exactly the kind that a ten-second `tzim --capabilities | jq`
would have settled.

## Findings

Severity: **A** — blocks a correct implementation, must be fixed before the coder starts; **B** — makes a document wrong,
fix before the first hand-over; **C** — cosmetic or explanatory.

### DR-01 · `tzim` now has a machine-readable capability document — severity **A**

Upstream: `--capabilities` prints one read-only JSON object, `capabilities_schema_version: 1`, declaring
`result_schema_version: 2`, `build_features`, `compiled_formats`, `default_enabled_formats`, `selection_flags`,
`handler_opt_ins`, `transformations`, `confirmation_policies` (`docs/cli.md` §"capabilities document",
[#85](https://github.com/RUdolf1517/tzim/issues/85), released in v0.16.0).

Our documents say the opposite, in several places:

| File | Line | Claim |
| --- | --- | --- |
| [docs/formats.md](../formats.md) | 27 | "there is no machine-readable capability list, and a guess would be a fabricated capability" |
| [docs/guarantees.md](../guarantees.md) | 37–39 | "Capabilities are build-dependent and there is no machine-readable […] do not report a capability we cannot observe" |
| [docs/limitations.md](../limitations.md) | 56 | "No machine-readable capability list: we record version and binary hash" |
| [docs/faq.md](../faq.md) | 62–64 | the same question, answered with the same obsolete fact |
| [ASSIGNMENT-AT-MVP-DRAFT](../manager/ASSIGNMENT-AT-MVP-DRAFT.md) | 98 | "`tzim` has no machine-readable capability list" |
| [QUESTIONS-TO-OWNER](../manager/QUESTIONS-TO-OWNER.md) | 67, 70 | ditto |
| [DECISIONS](../manager/DECISIONS.md) | D-22, row 30 | the upstream issue is described as future work |
| [GATES](../manager/GATES.md) | AC-13, INV-18 | acceptance rows written to prove the *absence* of a capability source |

The charter's P-01 limitation ("capability list absent, so delegate the default set and record version+hash") was a
correct reading of the old binary. It is now a false statement about the new one.

**Action:** rewrite the affected sentences to say the capability document exists; decide whether the MVP *consumes* it
(see DR-05 — this is an owner question, not a manager one); close D-22 as delivered; rewrite AC-13 and INV-18 so they test
"we never claim a capability we did not read", not "no such document exists".

### DR-02 · structured reasons exist — severity **A**

Upstream: every file row carries `reason_code` — a stable machine-readable identifier, `null` for
`optimized`/`would_optimize` (`docs/cli.md`, field table; released with v0.16.0). Consumers are told to treat an unknown
code as an unknown reason and never infer consent from it.

Our design says a refusal is one undifferentiated bucket with the human `note` kept verbatim:

| File | Line | Claim |
| --- | --- | --- |
| [docs/cli.md](../cli.md) | 93, 136 | `skipped_by_tzim` rows carry the raw status and note; the note is "never a classification key" |
| [docs/faq.md](../faq.md) | 57 | "why one bucket?" |
| [docs/formats.md](../formats.md) | 20 | a refusal is `skipped_by_tzim` with `tzim`'s own words |
| [docs/guarantees.md](../guarantees.md) | 34, 51 | "arrives as one generic `skipped_by_tzim`" |
| [docs/limitations.md](../limitations.md) | 44 | "it is not typed" |
| [GATES](../manager/GATES.md) | INV-18 | no prose may be used as a reason |

`INV-18` survives — parsing a human `note` is still forbidden. What changes is that a typed field now exists, so the MVP
can pass a stable code through instead of collapsing every refusal into one bucket. This is an improvement to the user's
output, and a **contract change** in our own JSON (`counts`, `reason`): it needs an owner decision, not a quiet edit.

### DR-03 · the pinned binary is obsolete, and a fixture hard-codes it — severity **A**

| File | Line | Claim |
| --- | --- | --- |
| [FIXTURE-CORPUS](../manager/FIXTURE-CORPUS.md) | 99 | case `A-01`: `--version` → `tzim 0.14.0` |
| [ASSIGNMENT-AT-MVP-DRAFT](../manager/ASSIGNMENT-AT-MVP-DRAFT.md) | 96 | the suite "pins `tzim v0.14.0`" |
| [docs/testing-harness.md](../testing-harness.md) | 36, 122, 123 | the pinned fetcher example uses `0.14.0` |
| [docs/formats.md](../formats.md) | 28 | the release binaries "of `tzim` `0.14.0`" are described |
| [ROADMAP-ISSUES](../manager/ROADMAP-ISSUES.md) | 95 | the fake-binary version matrix starts at `0.13.9` |

Two problems, not one. The version is three releases behind (**the current release is v0.16.1**), and a frozen fixture
carries the literal string, so the corpus would fail the moment AT-08 pinned the current binary — which is precisely the
kind of self-inflicted red that erodes trust in a green run. The fixture should pin **the version as a variable** and
assert the *shape* (`tzim <semver>`), with the concrete version supplied by the pin file.

### DR-04 · `--dry-run` exists now; our ban is still right, for a different reason — severity **B**

Upstream: `-n, --dry-run` performs the complete pipeline — detection, candidate generation, verification — skips only the
rename, **creates a real candidate in the destination directory** and deletes it afterwards (`docs/cli.md` §6).

Our P-02 ("`tzim --dry-run` is forbidden in the MVP") was derived partly from the flag not existing. The ban stands, and
the reason is now sharper: the flag exists, and it writes. Documents that say or imply it is absent are wrong:
[architecture.md](../architecture.md) 24, 83; [cli.md](../cli.md) 65, 78, 196; [faq.md](../faq.md) 21–22.

Secondary point: our own `run --dry-run` (an alias of `scan`) now collides in name with a real `tzim` flag. Our flag means
"plan, touch nothing"; `tzim`'s means "do the work, write a temporary candidate". The documentation must say so in one
sentence where the two are first compared.

### DR-05 · the delegated default set changed — severity **A** (owner decision)

Our policy (D-01, P-01) is: never pass `--formats`, delegate the default set to the binary. In v0.16.x that default now
includes JPEG when the build has `jpeg-v1` (upstream [#82](https://github.com/RUdolf1517/tzim/issues/82),
[#90](https://github.com/RUdolf1517/tzim/pull/90)), alongside png, gzip, zip, ico, tiff, zlib. The compile-time opt-ins
(FITS, FLAC, PDF) are still separate and still excluded from `default_enabled_formats`.

So "delegate the default set" is no longer the same set it was when the decision was taken, and it silently decides which
of the user's files get modified. That is a product-policy question, and the answer belongs to the owner:
**keep delegating regardless of build, or require `--capabilities` to prove what the default set is before planning?**
The second option is only possible because of DR-01, and it is strictly more honest.

### DR-06 · FITS confirmation shipped; our no-PTY rule still holds — severity **B**

Upstream: an interactive default-No confirmation for `--fits-tile` on a single direct file on a TTY; no prompt for
non-TTY, `--json`, `--dry-run`, recursive or multi-file runs; a refusal is `skipped` with the original byte-identical
(`docs/cli.md` §"FITS tile confirmation"). Our D-21 (no PTY, `stdin=DEVNULL`, per-file timeout, a child that waits is
killed and recorded `failed`) is correct and unaffected — but [UPSTREAM](../manager/UPSTREAM.md) still describes the
prompt as future work, and the corpus has no case for "a binary that prompts while our stdin is `/dev/null`".

### DR-07 · exit-code details became explicit — severity **B**

Upstream v0.16.1 fixed and documented the precedence ([#109](https://github.com/RUdolf1517/tzim/pull/109)):

- a missing or unreadable input path is a per-file failure and exits **1** (not 2, not 3);
- `EPIPE` does **not** replace an already-earned code — `0`, `1` or `4` survives a closed pipe;
- any other stdout write error exits **3**, unless verification code **4** was already earned, in which case **4** wins;
- OOM is **not** promised to map to 3 (`panic = "abort"`).

Our own exit contract is separate (P-03) and our matrix (`X-01…X-16`) maps `tzim` codes to ours. That mapping must be
re-derived against these rules, and the "tzim exit 4 ⇒ our 1" row keeps its meaning but needs the EPIPE case beside it.

### DR-08 · new informational and resource flags exist — severity **C**

`--info`, `--list-formats`, `--check-deps`, `--capabilities`, `--jobs`, `--memory-budget`, `--min-size`/`--max-size`,
`--max-pixels`, `--max-uncompressed`, `--max-ratio` all exist in v0.16.1. Our adapter passes none of them, which is the
intended behaviour, but `A-10` in the frozen corpus was justified as "the flags we must never probe"; two of those flags
are now the *supported* way to ask. Update the rationale, keep the tripwire.

### DR-09 · our adapter version table is re-derived from an old binary — severity **B**

`adapter: "tzim-0.14"`, the accepted version set and the `incompatible_tzim` fallback were written against `0.14.0`.
Unknown versions must still fail closed; the known-version set needs an owner-approved window (e.g. `>=0.16.0, <0.17`
consuming `capabilities_schema_version: 1` / `result_schema_version: 2`), otherwise the first user with v0.16.1 gets
`incompatible_tzim` for no reason.

### DR-10 · upstream tracker state in our documents is stale — severity **C**

[UPSTREAM](../manager/UPSTREAM.md) lists `#83`, `#82`, `#78`, `#79`, `#80`, `#85` as open. All are closed; `#86` is
closed as a duplicate; `#84` is merged; three releases have shipped since. A document that tracks someone else's tracker
must carry a read date, and this one now does.

## Findings that did not change

For completeness, so the next audit does not re-check them from scratch:

- the six statuses (`optimized`, `would_optimize`, `already_optimal`, `unsupported`, `skipped`, `failed`) and the four
  error kinds (`io`, `parse`, `verify`, `internal`) are unchanged;
- hard links are still skipped unless `--allow-hardlinks`; symlinks are still not followed by default;
- exit codes are still `0/1/2/3/4` with the same meanings;
- there is still no stdin/prompt code on any non-TTY path, and no capability to write anywhere except a candidate in the
  destination directory;
- release assets still carry stable unversioned URLs and a `SHA256SUMS`, so the pinning story in
  [testing-harness](../testing-harness.md) works as designed — with a new version number.
