## 1. Lock: D-53 answered it, D-54 refined it

The lock question is closed: **`std::fs::File::try_lock()`**, MSRV **1.89**, no `unsafe`, no `libc`, no wrapper crate. The
lock file is `0600`, is **never deleted**, its contents are diagnostics only, contention is exit `8`. Stale locks do not
exist because the kernel releases them when the process dies — that is the whole point of the decision, and your SIGKILL
test proves it.

## 2. `config validate` must not take the lock (F-21 — this is the defect)

`cli.md` §2.2 promises `config validate` works **without touching state**, and taking the lock creates
`$AUTO_TZIM_HOME/locks/`. Fix: `config validate`, `folder list` and `folder show` take **no** lock and create nothing;
every mutating command keeps the lock exactly as it is. Readers do not need it — a config write is an atomic rename, so a
reader sees the old file or the new one and never a half-written one.

Add the control: point `AUTO_TZIM_HOME` at a path that does not exist, run `config validate`, and assert that **no file or
directory was created**.

## 3. `mode = "auto"` is valid — your reading of the rule is too strict

`config.md` says a *default* of `auto` is refused. That is not "only `confirm` is accepted". The default value must stay
`confirm` — destruction by default is not a convenience — but a user who writes `mode = "auto"` has chosen it in the file,
which is exactly what the two modes are for. Accept `confirm` and `auto`; reject everything else with a message that says
which values are allowed, **not** "default must be confirm".

Add the two cases: `mode = "auto"` → exit `0`; `mode = "sometimes"` → exit `2` naming both allowed values.

## 4. `tzim_path` must be real

A non-empty `tzim_path` is checked in `config validate`: absolute, not a directory, **exists**, **regular file**,
**executable** — otherwise exit `2` with `tzim_path_missing` or `tzim_path_not_executable`. Empty means "find `tzim` on
`PATH`", and that lookup belongs to the adapter at run time, not to `validate`. Rationale: a named path that is not there
is a typo, and catching typos before a run is what `validate` is for.

## 5. `--allow-cloud-sync` / `--no-allow-cloud-sync` exist

Add both to `folder add` and `folder edit`; they set `allow_cloud_sync`. D-44's escape hatch has to be reachable from the
command line, otherwise the only people who can use it are those who hand-edit TOML — in a tool whose point is not editing
TOML by hand. The refusal message stays as it is (`cloud_sync_root: use allow_cloud_sync = true to override`) so the flag
is discoverable at the moment it is needed.

## 6. Permissions: your control is accepted, add one repair test

Removing `set_permissions` **and** the safe creation modes and seeing `0666` proves the protection as a whole, and that is
the right thing to prove — briefly making a file `0666` to test a single `chmod` would be worse than the gap it closes. So
keep the control. Add the other side: take a config that is **already** `0666`, run any mutating command, and assert it
ends `0600`. Together they prove both layers without ever loosening anything.

## 7. Lock metadata: diagnostics, and honestly named

`start_time` currently holds the process **entry** time. An OS-reported creation time is not available without a
dependency, and [D-38](DECISIONS.md) forbids a dependency for cosmetics. Rename the field to `started_at` — a name that
describes what it holds — or drop it. Do not add a crate. `host` is `HOSTNAME` when set and **omitted** when not: never
the literal string `"unknown"`, which reads like a host called unknown.

Nothing reads these fields; they exist so the human who gets exit `8` can see who holds the lock. Say so in one comment.

## 8. Stale temp cleanup: yes, and here is why it is safe

`remove_stale_temps` after a successful rename is correct **because** the lock is held: every writer takes `config.lock`,
so any `.config.toml.<ts>.<n>.tmp` present under the lock belongs to a dead process. Keep it scoped exactly as it is — the
config directory only, our exact name pattern, never recursive. Without the lock this would be the unsafe deletion you
were right to refuse.
